## 1. 三个项目的实际实现

### 1.1 QingZai

- 纯 Kotlin 客户端，44 个文件；Compose + Hilt + Room + OkHttp + Media3 + WorkManager；minSdk 26，targetSdk 35。
- 解析链：`ContentRepository.parseUrl()` → 短链用 OkHttp `HEAD` 跟随 → `HtmlParser.extractIds()` 取 `video/note` 的 aweme_id → 请求 `https://www.iesdouyin.com/share/{video|note}/{id}/`。
- **关键实现**：`DouyinApi.fetchPage()` 连续请求两次，第一次只为让 `CookieJar` 保存抖音下发的 `ttwid`，第二次带 cookie 才解析 `window._ROUTER_DATA`。`hasContent()` 用 `videoInfoRes / item_list / playwm / play_addr` 四个关键词判断。
- 视频：正则取 `playwm` URL，把 `playwm` 替换成 `play` 作为“无水印”地址；标题取 `desc`，作者取 `nickname`，封面取 `cover.url_list`。
- 图集：在 `_ROUTER_DATA` 中找 `"images":[{`，再按方括号配对截取，取每个 `url_list[0]`；同时取 `music.uri` 与 `duration`。
- 单图作品（动图/LivePhoto）：`AnimatedVideoResolver` 新建 WebView 打开 `https://www.douyin.com/note/{id}`，拦截 `douyinvod` 请求或读 `<video>.src`，15 秒超时，失败回退页面里的 douyinvod 字符串。
- 下载：带 `Referer: https://www.douyin.com/`，30 秒超时、3 次重试；WorkManager + 通知。
- 未发现任何第三方解析 API、Docker 服务或云端依赖。

**对当前项目的直接价值**：它解释了“为什么我们之前的直连总是拿不到 `play_addr`”——请求没有持久化 `ttwid` cookie。本机复测已证实这一点（见 §3）。

### 1.2 douyin-material-saver

- 纯 Java/Kotlin 客户端，GPL-3.0，minSdk 29，targetSdk 36；不使用 Python、不依赖外部服务。
- 核心 `DouyinInspector.java`（690 行）：
  - 隐藏/后台 WebView 打开作品页，`shouldInterceptRequest` 捕获页面自己发出的 `GET /aweme/v1/web/aweme/detail/` 请求（带 aweme_id 校验）；
  - 用 `HttpURLConnection` **原样重放**该请求，并带上 WebView 的 Cookie 与 `uifid`、UA、Referer、sec-ch-ua 等允许头，拿到详情 JSON；
  - 详情接口被平台过滤（图集被裁掉）时，改为从页面 `__pace_f`、`_ROUTER_DATA`、`RENDER_DATA`、`SSR_RENDER_DATA` 等读取，按 aweme_id 精确匹配；
  - 页面加载后 0/1.5/4/8 秒做页面数据探测，12 秒总超时；检测验证码/登录页并提示用户完成验证。
- `MediaSelector.java`（1118 行）：同时兼容详情接口 snake_case 与页面驼峰字段，支持视频多码率、图集、LivePhoto、BGM，过滤水印候选。
- 下载：前台服务 + MediaStore，保存到 `DCIM/抖音素材`；日志明确不输出签名参数与 Cookie。

**结论**：这是“最稳”的路线，但代码体量大、GPL-3.0 不可复制，且 minSdk 29 高于当前项目的 24。

### 1.3 DouyinKit

- 纯 Kotlin 客户端，MIT，minSdk 24，targetSdk 36；Compose + Room + OkHttp；APK 约 3.44MB（R8）。
- 解析核心：
  - `DouyinWebViewEngine.kt`（708 行）持有唯一 WebView，文档开始时注入 `assets/parser/hook.js`（377 行），并注入 `page_model.js`（167 行）做页面对象扫描；
  - `hook.js` 重写 `fetch` 与 `XMLHttpRequest`，只监听 `/aweme/v1/web/aweme/detail/`，把返回的 `aweme_detail` 压缩后通过 JS Bridge 回传 Kotlin；不 eval、不把完整 JSON 落盘；
  - `page_model.js` 在页面对象树中按 `aweme_id` 找 `video.bitRateList/play_addr/images`，作为接口被过滤时的兜底；
  - `ParseController.kt`（592 行）：详情超时 45 秒；检测到滑块/验证码时把超时延长到 120 秒并提示；登录页与安全验证分开处理；错误码枚举（`NO_LINK/SHORT_LINK_TIMEOUT/DETAIL_TIMEOUT/NO_MEDIA/NEEDS_VERIFICATION/NEEDS_LOGIN/...`）；
  - `DouyinDetailNormalizer.kt`（681 行）：统一处理 snake_case 与 camelCase，支持视频多档清晰度（H.264/H.265）、图集、LivePhoto、BGM、封面，字段全部可选；
  - 短链用 `GET` 读 `Location` 解析（不用 HEAD），并校验跳转后的域名仍是抖音。
- 下载：OkHttp + MediaStore，支持 Range 续传、magic 校验、通知；另有悬浮球/无障碍等扩展，本任务不需要。

**结论**：MIT、纯本地、minSdk 24、对图集/LivePhoto/多清晰度/错误分类覆盖最完整，且“钩子抓签名请求”比“自己复刻签名”稳定得多。

## 3. 本轮本机验证（仅证明可行性，不代表 Android 已通过）

对 `https://www.iesdouyin.com/share/video/7388149561765760266/`，iPhone UA + `Referer: https://www.douyin.com/`，Python `requests.Session`：

1. 第 1 次请求：HTTP 200，32,334B，`play_addr` 0 次，只拿到 `ttwid`。
2. 第 2 次请求（自动带 `ttwid`）：HTTP 200，37,930B，`play_addr` 1 次，`playwm` 1 次，`videoInfoRes/item_list` 各 1 次。
3. 解析出的地址：`https://aweme.snssdk.com/aweme/v1/playwm/?video_id=...&ratio=720p&line=0`。
4. 对 `playwm` 与把 `playwm` 换成 `play` 的地址分别请求 `Range: bytes=0-1023`：均 **206 `video/mp4`**，`Content-Range: bytes 0-1023/420828761`，1024 字节。

结论：
- **直连公开分享页可解析公开视频，前提是保留 `ttwid` 并请求两次。** 这解释了当前项目“直连无数据”的主因，不是抖音完全关闭了 SSR。
- 该地址是否为无水印版本、以及公开图集是否同样返回，**尚未验证**；需要真机/有效图集链接复测，文档与代码不得提前宣称。
- 早前 PC 无头 Edge 打开桌面作品页拿到的 `v11-weba.douyinvod.com` 地址（774,782,271B）是另一条 CDN 路径，可作为 WebView 兜底的结果，但不能当作稳定接口。

## 4. 对用户 8 个问题的回答

1. **哪个最适合移植？** DouyinKit 的“WebView 钩子 + 归一化 + 错误码”整体思路最适合移植；QingZai 的“两次请求 + cookie”最适合作为快速路径先实现。二者都是 MIT。
2. **哪个最适合 Android 本地运行？** 二者都是纯本地；DouyinKit 覆盖图集/LivePhoto/多清晰度/验证码，工程完整度更高；QingZai 更轻，适合先落地原生 HTTP 通道。
3. **能否不依赖第三方 API 解析公开视频和图集？** 视频：本轮已在 PC 验证可行（cookie 双请求）。图集：QingZai/DouyinKit 源码均实现了从分享页或详情接口读取 `images`，但**本轮没有有效图集链接，未做网络验证**，需要在阶段 4 用真机补测。
4. **哪些代码/技术可以合法复用？** QingZai 与 DouyinKit 均为 MIT，可复用并在 `THIRD-PARTY-NOTICES` 保留版权与许可文本；douyin-material-saver 为 GPL-3.0，**不复制任何代码**，只参考公开思路。建议以独立实现为主，必要时再引入 MIT 片段并注明来源。
5. **能否保留 Kotlin + Chaquopy + Python 架构？** 可以。抖音解析放在 Kotlin（网络/WebView 都更顺），通过现有 `DouyinResolver.resolve()` 桥把统一 JSON 交给 Python；Python 继续负责扫描、下载、转换、HTTP 服务与前端。
6. **如何衔接 WebView、下载器和统一数据结构？** 桥返回 `{ok, items:[...], error_code, error}`；Python 归一成现有 item 结构（`kind/url/thumb/name/ext/size/w/h/referer/source/via/page`），图集直接复用现有 grid 与批量下载；`/api/dl` 继续带 Referer 与过期重解析。
7. **F1/F2/F5/F7/F8 怎么解决？**
   - F1：SSE 空闲阈值从 8s 提到 45s，并在 engine 阶段每 3s 发心跳；原生快速路径通常 2–6s 返回，减少长等待。
   - F2：桥从“单 video”改为“items 列表”，图集与视频统一输出。
   - F5：第三方 API 链默认关闭，仅在显式开启时执行，且排在原生/WebView 之后；不再作为“本地解析”的一部分。
   - F7：把 WebView 放进独立、可配置变化的透明 `ParseActivity`（或前台服务 overlay），不再依赖 `currentActivity`；页面销毁不影响解析。
   - F8：Kotlin 返回明确 `error_code`（`NEEDS_VERIFICATION/NEEDS_LOGIN/PAGE_LOAD_FAILED/DETAIL_TIMEOUT/NO_MEDIA/...`），前端显示对应中文并提供“打开页面/完成验证”入口。
8. **体积/内存/耗时影响？**
   - APK：只新增 JS 资产（约 20KB）与 Kotlin 类，不新增 native 库；预计 +0.3–0.8MB。
   - 内存：解析期间一个隐藏 WebView 约 80–200MB，必须单实例、解析完销毁/复用；原生 HTTP 通道几乎不增加内存。
   - 耗时：原生通道 2–6s；WebView 通道常见 7–22s，详情超时 45s，验证场景最长 120s；应优先原生、失败再起 WebView。

## 5. 推荐结论

采用 **“原生 HTTP 快速通道 + WebView 钩子兜底”** 的双通道，落在现有 Kotlin 桥内，Python 只做适配：

- 通道 A（优先）：Kotlin OkHttp + 持久 Cookie，短链展开 → 两次请求分享页 → 解析 `_ROUTER_DATA` → 视频/图集统一输出。对应 QingZai 的已验证思路，独立实现。
- 通道 B（兜底）：独立透明 Activity 承载 WebView，文档开始注入钩子，捕获 `/aweme/v1/web/aweme/detail/` 的 JSON；失败再读页面模型；对应 DouyinKit 的思路，独立实现。
- 通道 C（可选、默认关闭）：保留现有第三方 API 代码，但不在默认链路中执行；仅作为用户显式开启的应急手段，并在 UI/文档中说明它会把链接发给第三方。

这样既满足“完全本地、不依赖第三方 API”，又避免一次性把 1,400 行 Kotlin 全量移植带来的风险；每一层都能单独测试、单独回滚。
